# 패브링 보안 점검 결과와 개선 우선순위

> 저장소 보관본: 아래 내용은 점검 당시의 기록이다. 이후 사용자 요청으로 보안 브랜치에 커밋·푸시하며, 로컬 경로·시험용 서명값은 공개용으로 정리했다. 원본 증거와 ZIP은 로컬에 보존한다.


점검일: 2026년 10월 13일

**HTTP 요청으로 보안 문제 4건을 재현했고, 모의 HTTP 응답으로 AI 타임아웃 결함 1건을 확인했다.** 우선 개선할 항목은 비밀번호의 UTF-8 바이트 처리, 로그아웃 시 서버 토큰 폐기, 사진의 공개 권한과 삭제 정책, 사용자별 AI 비용·동시 호출 제한이다.

관리자 권한 우회, 타인 예약·원단 변경, 비공개 문의 원문 접근, 변조·만료 JWT, 부적절한 업로드와 예약 동시 처리에서는 준비한 시나리오가 차단됐다. 이는 확인한 시나리오의 결과이며 ASVS 전체나 특정 레벨의 충족 판정은 아니다.

## 개선 우선순위

P0는 공개 또는 실제 AI 활성화 전에 완료할 작업, P1은 다음 보안 작업에서 처리할 항목, P2는 운영 정책과 유지보수 항목이다. 심각도는 이 서비스의 재현 조건과 영향을 고려한 정성 평가이며 CVSS 점수가 아니다.

## F1 비밀번호가 72바이트 이후의 차이를 구별하지 못함

등록 API에 한글 24자와 ASCII 접미사 1자를 합친 25자 비밀번호를 보냈다. UTF-8로는 73바이트지만 가입은 201로 성공했다. 접미사만 바꾼 다른 비밀번호로 로그인했을 때도 200이었다. 운영 설정과 같은 bcrypt cost 10으로 직접 비교해도 같은 현상이 재현됐다.

원인은 문자열 길이 `.max(72)`와 bcrypt 입력의 72바이트 제한이 다르기 때문이다. ASCII의 일반적인 72자 이하 비밀번호와, 72바이트까지 서로 다른 비밀번호 전체가 임의로 같게 검증된다는 의미는 아니다. 첫 72바이트가 같고 뒤가 다른 입력에서 발생한다.

근거: [auth.schema.js 5행](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/validators/auth.schema.js%3A5), [auth.service.js 14행](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/services/auth.service.js%3A14). 증거 ID는 `V01`이다.

직접 기준은 [ASVS v5.0.0-6.2.8](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x15-V6-Authentication.md)과 [OWASP 비밀번호 저장 가이드](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)다. KISA는 제2장 제2절 9번, 책자 85쪽·PDF 91쪽의 패스워드 검토 주제로 연결한다. KISA 절이 bcrypt의 72바이트 제한을 직접 규정한다는 의미는 아니다.

**개선:** 신규 가입·비밀번호 변경에는 UTF-8 바이트 길이를 검증하거나 긴 입력을 온전히 처리할 해시로 전환한다. 입력을 임의로 잘라 통과시키지 않는다. 기존 긴 비밀번호 계정의 로그인 호환성·재설정·재해시 이행 방식도 정해야 한다. 확인 없이 로그인에 바이트 제한만 추가하면 기존 사용자가 로그인하지 못할 수 있다.

**재점검:** ASCII·한글·이모지의 경계값, 첫 72바이트가 같은 두 입력, 기존 해시 계정의 로그인과 이행을 함께 확인한다.

## F2 로그아웃해도 복사한 JWT가 계속 유효함

현재 프론트 adapter로 실제 로컬 계정에 로그인하고 JWT를 테스트 메모리에 보관했다. adapter의 `logout()`을 실행하자 sessionStorage는 지워졌지만, 보관한 토큰으로 `/users/me`를 호출하면 200이었다. 테스트 설정에서 발급 토큰 수명은 24시간이다.

클라이언트 로그아웃은 수행되지만 서버에서 해당 세션을 종료할 계약이 없다. 공격자가 토큰을 이미 취득한 경우, 사용자의 로그아웃으로 그 토큰 사용을 중단시킬 수 없다. 이 시험에서 토큰을 훔치는 공격까지 재현한 것은 아니다.

근거: [live-api.js 598행](https://github.com/goduckTeam/Frontend/blob/security/p0-hardening-20261014/src/react/services/live-api.js%3A598), [auth.js 14행](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/middlewares/auth.js%3A14). 증거 ID는 `V02`다.

직접 기준은 [ASVS v5.0.0-7.4.1](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x16-V7-Session-Management.md)이다. KISA는 책자 62쪽·PDF 68쪽의 서버 인증 주제와 연결하지만, JWT 폐기 방법을 KISA의 특정 요구사항으로 간주하지 않는다.

**개선:** 서버 세션 또는 토큰 식별자 폐기 목록, 계정의 토큰 발급 유효 시각 같은 방식을 선택하고 실제 로그아웃 API와 연결한다. 여러 서버에서는 폐기 상태를 공유해야 한다. 토큰 수명 축소만으로 즉시 폐기가 구현되지는 않는다.

**재점검:** 같은 토큰의 로그아웃 전 200과 종료 후 401, 여러 탭, 계정 변경, 서버 재시작·여러 서버 조건을 확인한다.

## F3 원단의 조회 권한이 사진 다운로드에 적용되지 않음

승인 대기 원단 상세를 비로그인으로 조회하면 404였다. 같은 원단의 사진 URL을 비로그인으로 요청하면 원본이 200으로 반환됐다. 원단 소유자가 삭제 API를 실행한 뒤에도 상세는 404지만 기존 사진 URL은 여전히 200이었다.

UUID 파일명을 사용하므로 URL을 모르는 사람이 쉽게 열거했다는 결과는 아니다. 이미 공유되거나 이전에 얻은 URL은 비공개·삭제 상태에서도 계속 사용할 수 있었다. 원단 삭제 API는 soft delete를 처리하지만 해당 이미지의 공개 제공을 중단하지 않는다.

업로드한 원본과 내려받은 파일의 바이트가 같았으며, 가상 EXIF 작성자 마커도 유지됐다. 실제 사용자의 위치정보가 유출됐다고 판정한 것은 아니다. 위치나 개인 식별 정보가 포함된 원본에서는 함께 노출될 수 있다.

근거: [app.js 21행](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/app.js%3A21), [images.service.js 53행](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/services/images.service.js%3A53), [fabrics.service.js](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/services/fabrics.service.js). 증거 ID는 `V03`이다.

직접 기준은 [ASVS v5.0.0-8.2.2](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x17-V8-Authorization.md)이며, 메타데이터 정책은 [v5.0.0-14.2.8](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x23-V14-Data-Protection.md)과 연결한다. KISA의 권한 주제는 책자 65쪽·PDF 71쪽에서 확인했다.

**개선:** 모든 상태의 사진을 같은 공개 폴더에서 제공하는 방식을 바꾼다. 비공개 사진은 서버 권한 검사 또는 짧은 수명의 서명 URL로 제공하고, 공개 원단에 필요한 변환본만 공개한다. 원단 삭제와 사진 제공 중단을 연결한다. 원본을 내부 보관할지, 삭제할지와 보관 기간을 정하고 공개 이미지에서는 불필요한 EXIF를 제거한다.

**재점검:** 승인 대기·반려·게시·삭제 상태별로 비로그인, 소유자, 다른 판매자의 원본·썸네일 요청을 비교한다. 삭제 후 과거 URL과 캐시도 확인한다.

## F4 승인 판매자의 AI 호출량과 동시 처리를 제한하지 않음

한 승인 판매자가 사진 분석 API를 동시에 24번 호출했다. 전부 200이었고 제공자는 24회 호출됐으며 동시 제공자 호출의 최대값도 24였다. 같은 계정의 AI 세션 시작 요청 24개도 모두 201이었다. 미승인 판매자는 403으로 차단됐다.

시험에는 계수용 가짜 제공자를 사용했다. 실제 비용 증가나 서비스 장애를 일으킨 것은 아니다. 현재 라우트·서비스에 계정별 호출량, 전체 예산과 전역 동시 처리 제한이 없어, 실제 제공자를 켠 경우 승인 판매자의 반복 요청이 비용·CPU·메모리를 소비할 수 있다. 세션별 잠금은 서로 다른 세션이나 사진 분석 전체의 호출량을 제한하지 않는다.

단일 AI 응답의 최대 토큰과 실패 재시도 2회 제한은 존재한다. 이것으로 한 계정이 만드는 총 요청 수나 동시 처리량을 제한하지는 못한다. 배포 계층에 별도 제한이 있는지는 운영 환경에서 추가 확인해야 한다.

근거: [aiSessions.routes.js 17행](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/routes/aiSessions.routes.js%3A17), [aiPhoto.service.js 47행](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/services/aiPhoto.service.js%3A47), [aiRegistration.service.js](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/services/aiRegistration.service.js). 증거 ID는 `V04`다.

직접 기준은 [ASVS v5.0.0-2.4.1](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x11-V2-Validation-and-Business-Logic.md)과 [v5.0.0-15.2.2](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x24-V15-Secure-Coding-and-Architecture.md)다. KISA의 유한 자원 관리 주제는 책자 121쪽·PDF 127쪽으로 연결하며, 이 절이 AI 일일 예산을 규정한다는 의미는 아니다.

**개선:** 외부 호출 전에 사용자별 요청·토큰·비용 한도와 전체 예산을 예약한다. 계정별·전체 동시 처리 한도, 대기열 크기, 활성 세션 수, 업로드 총량을 정한다. 실패 재시도에도 같은 예산을 적용하고 여러 서버에서는 한도 상태를 공유한다.

**재점검:** 한도 이하 요청의 정상 처리, 초과 요청이 외부 제공자를 호출하지 않음, 동시에 여러 세션·여러 서버로 요청해도 한도를 우회하지 못함을 확인한다.

## F5 AI 응답 본문의 지연에는 타임아웃이 적용되지 않음

실제 제공자 모듈에 헤더는 즉시 반환하지만 본문 읽기는 지연하는 모의 HTTP 응답을 넣었다. 타임아웃은 20ms였으나 108ms 시점에도 호출이 대기했고 AbortSignal은 중단되지 않았다. 시험 종료를 위해 본문을 명시적으로 반환했다.

원인은 `fetch()`가 헤더를 반환한 직후 `finally`에서 타이머를 지우고, `response.json()`은 그 다음에 실행하는 순서다. 실제 외부 AI에 지연 요청을 보낸 시험은 아니다. 제공자 모듈의 전체 요청 시간 제한이 본문 수신을 보호하지 못하는 결함을 확인했다.

근거: [claudeProvider.js](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/ai/claudeProvider.js). 증거 ID는 `V05`다. 직접 기준은 ASVS 15.2.2와 [16.5.2](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x25-V16-Security-Logging-and-Error-Handling.md), KISA 연결 주제는 책자 113쪽·PDF 119쪽의 오류 대응과 책자 121쪽의 자원 반환이다.

**개선:** 타이머 해제는 응답 본문 읽기까지 포함한 전체 작업의 `finally`에서 수행한다. 응답 크기 상한과 전체 재시도 시간 예산도 정한다. 본문 지연 시 요청이 종료돼야 관련 잠금과 동시 처리 자원도 반환할 수 있다.

**재점검:** 헤더 지연, 본문 지연, 잘못된 JSON, 제한 초과 본문, 클라이언트 취소, 재시도와 큐 자원 반환을 모의 제공자로 검증한다.

## 추가 보완과 보류 항목

개인정보 응답에는 서버 `Cache-Control: no-store`를 적용한다. 프론트 fetch의 `cache: no-store`는 서버와 중간 캐시의 정책을 대신하지 않는다. 기준은 ASVS 14.3.2이며 증거 ID는 `G01`이다.

로그인 성공·실패, 권한 거절, 관리자 승인·반려, 한도 초과를 구조화해서 남기고 토큰·비밀번호·문의 원문은 마스킹한다. 현재 코드에서 주로 확인한 로그는 예외의 `console.error`다. ASVS 16.2.1·16.2.5·16.3.1·16.3.2로 후속 점검한다.

확정 AI 세션은 현재 만료 정리 대상에서 제외돼 있다. 별도의 메모리 저장소에서 가상 시간을 365일 이동해도 유지됨을 확인했다. 실행된 서버가 실제로 365일 동작했다는 의미는 아니다. 대화·최종 데이터의 보관 기간과 전체 보관량을 정한다. 증거 ID는 `G02`다.

HTTPS, 정적 프론트의 CSP, CORS와 프록시 IP 신뢰, 여러 서버의 로그인 제한, 운영 DB의 TLS와 최소 권한, 운영 비밀값 저장 방식, 백업과 복원은 실제 배포 구성에서 확인해야 한다. Vite 개발 서버의 헤더로 운영 사이트의 헤더를 판정하지 않는다.

알려진 로컬 백엔드 비밀값과 새 프론트 빌드의 텍스트 파일 35개를 대조했고 일치 항목은 0개였다. 추적된 실제 `.env`·개인키 파일명도 확인되지 않았다. 전체 Git 이력이나 알려지지 않은 모든 비밀값을 검사한 결과는 아니다. 공개된 심사 체험 계정은 프론트의 시연 모드 분기와 구분했으며, 그 존재를 실제 관리자 API 우회로 집계하지 않았다.

## 기준 해석과 KISA 원문

KISA 원문은 공식 게시글에서 받은 159페이지 PDF를 사용했다. 책자 쪽수와 PDF 페이지는 6페이지 차이가 있으므로 함께 적었다. [KISA 공식 게시글](https://www.kisa.or.kr/2060204/form?cPage=1&langType=KO&postSeq=14&searchType=&searchWord=).

KISA 절과 ASVS ID의 연결은 패브링에서 정한 주제별 대응이다. 두 문서가 공인한 일대일 대응표는 아니다. 특히 KISA 책자 85쪽의 패스워드 구성·주기 변경 예시와 ASVS 5.0.0의 6.2.5·6.2.10은 정책이 다르다. 이 점검에서는 입력을 온전히 검증하는 ASVS 6.2.8을 직접 판정 기준으로 삼았다. 향후 비밀번호 정책은 최신 ASVS의 길이·취약 비밀번호 차단·유출 시 변경 정책을 기준으로 설계하고 KISA의 예시를 그대로 혼합하지 않는다.

## 실행할 개선 작업과 발표 활용

먼저 F1의 비밀번호 호환성 정책과 F2의 서버 세션 종료 계약을 확정해 수정한다. 이어 F3의 사진 제공 권한·삭제 정책을 맞추고, 실제 AI를 켜기 전에 F4의 예산·동시 처리와 F5의 전체 타임아웃을 구현한다. 각 항목의 변경 후에는 이 보고서의 같은 재현 요청과 정상 흐름을 다시 확인한다.

이후 자료 적재 도구의 취약 의존성을 정리하고 개인정보 캐시·보안 로그를 보강한다. 배포 방식이 확정되면 미확인 인프라 항목을 검증한다.

발표에는 F1의 다른 접미사 로그인, F2의 로그아웃 후 토큰 재사용, F3의 삭제 후 이미지 접근 중 실제 개선한 사례를 선정하면 전후가 명확하다. F4는 실제 과금을 일으키지 않고도 가짜 제공자의 호출 수와 한도 초과 차단으로 결과를 보여 줄 수 있다.

현재 상태는 문제 재현과 개선 계획이다. 수정·재점검이 끝난 항목에만 개선 완료 표현을 사용한다. 최신 작업 상태는 [점검표](패브링_보안점검표와_증거기록_2026-10-13.md)에서 확인한다.
