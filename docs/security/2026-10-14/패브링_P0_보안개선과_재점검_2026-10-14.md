# 패브링 P0 보안 개선과 재점검

> 저장소 보관본: 아래 내용은 점검 당시의 기록이다. 이후 사용자 요청으로 보안 브랜치에 커밋·푸시하며, 로컬 경로·시험용 서명값은 공개용으로 정리했다. 원본 증거와 ZIP은 로컬에 보존한다.


수정·재점검일: 2026년 10월 14일

요청한 **비밀번호 처리, 로그아웃 토큰 폐기, 사진 접근 권한, AI 호출 제한**을 수정하고 로컬 환경에서 재점검했다. 백엔드 520개 테스트와 별도 보안 시나리오 7개가 통과했다. 두 서버 프로세스·새 서버 프로세스에서도 토큰 폐기, AI 사용량과 세션 처리가 유지되는 것을 확인했다. AI 본문 타임아웃 결함 F5도 함께 수정했다.

이 결과는 선정한 요구사항과 시나리오에 대한 검증이다. ASVS 전체 레벨 충족이나 KISA 인증, 실제 공개 서버의 배포 완료를 의미하지 않는다.

## 수정 내용과 정상 동작

### 비밀번호

[입력 검사](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/validators/auth.schema.js), [가입·로그인 서비스](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/services/auth.service.js), [운영팀 계정 생성](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/db/seedAdmin.js), [프론트 연동](https://github.com/goduckTeam/Frontend/blob/security/p0-hardening-20261014/src/react/services/live-api.js)에 UTF-8 바이트 상한을 적용했다. bcrypt cost는 개발·운영 10, 시험 4를 유지했다. 단순 자르기·공백 제거·대소문자 변경은 하지 않는다.

원래 길이를 확인한 신규 비밀번호는 `users.password_byte_length`에 기록한다. 기존 해시는 원래 길이를 알아낼 수 없으므로 NULL로 남는다. 긴 기존 입력의 접미사를 거절하는 것만으로는 접두사 우회가 남기 때문에, 기존 해시의 정확히 72바이트 입력도 거절했다. 기존 72바이트 미만 비밀번호와 새로 가입한 72바이트 경계값은 정상 로그인했다. 한글·이모지 상한, 시드 상한, 서비스 계층 상한을 자동 테스트로 확인했다.

**호환성:** 기존 경계값 계정은 본인 확인을 거친 재설정이 필요하다. 현재 재설정 API는 없으며, 실제 해당 사용자가 있다면 복구 절차가 배포의 선행 조건이다. 모든 Unicode 비밀번호 64자를 허용하는 ASVS 6.2.9를 완전히 충족하려면 Argon2id 등 긴 입력을 처리하는 방식과 기존 계정 이행을 추가해야 한다.

### 로그아웃

새 `POST /auth/logout`에 프론트를 연결했다. [인증 미들웨어](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/middlewares/auth.js)가 DB의 폐기 지문을 확인하고, 새 JWT에는 독립적인 jti를 넣는다. [보안 서비스](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/services/security.service.js)는 원문 JWT를 보관하지 않는다. 프론트는 로컬 정보부터 제거하고 서버에 종료를 요청하며, 연결 실패에는 서버 종료를 확인하지 못했다는 안내를 표시한다.

HTTP 증거 R02는 실제 프론트 adapter로 로그인·로그아웃했다. 별도로 브라우저에서 정상 구매자 로그인, 홈 진입, 로그아웃, 로그인 화면 복귀를 확인했다. [브라우저 결과](fix-2026-10-14/browser-results.json), [화면 증거](fix-2026-10-14/browser-logout.png).

종료 대상은 로그아웃한 현재 JWT다. 다른 기기의 모든 토큰 종료나, 이미 인증 검사가 끝난 요청의 실행 취소는 이번 기능 범위에 포함하지 않는다. 서버 연결 실패 시 원격 폐기를 성공했다고 표시하지 않는다.

### 사진

[사진 권한 서비스](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/services/imageAccess.service.js)와 [다운로드 경로](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/app.js)에서 DB의 원단·사진 연결·삭제 상태를 확인한다. POSTED 사진은 공개하고 비공개 사진은 소유자·ADMIN Bearer 또는 권한 있는 API가 발급한 300초 서명 URL로 읽는다. 브라우저의 일반 `<img>` 표시를 위해 서명 링크를 사용한다. URL 보유자에게 기간 내 읽기 권한이 전달되므로 이 링크는 공유하지 않는 정보로 취급한다.

공개 API에는 서명을 붙이지 않아 게시를 내렸을 때 기존 공개 URL로 접근할 수 없다. 관심 목록도 비공개·삭제 원단의 썸네일을 발급하지 않는다. 본인 예약 조회는 당사자에게 허용된 기록의 사진 링크를 발급한다. 삭제된 원단·사진은 유효 서명도 차단한다. 새 업로드는 재인코딩하고, 기존 메타데이터가 있는 파일도 전송 전에 제거한다. 응답에 no-store와 no-referrer를 적용했다.

300초 사진 링크는 JWT와 별개의 제한된 읽기 권한이며 로그아웃 이후에도 만료 전까지 사용할 수 있다. 과거에 내려받은 파일·이미지 사본은 회수할 수 없다. 기존 저장 파일과 백업의 EXIF는 이번 코드로 직접 지우지 않고 응답에서 제거한다.

### AI

[DB 예약·한도 서비스](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/services/security.service.js)와 [DB DAO](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/dao/security.dao.js)를 사진 분석·대화 추출에 공통 적용했다. 실제 제공자 호출의 모든 시도가 사용량을 소비한다. 실패·기존 재시도도 포함하고, 초과 429는 재시도하지 않는다. 동시 슬롯은 finally에서 반환한다.

| 대상 | 계정별 기본값 | 서비스 전체 기본값 |
| --- | ---: | ---: |
| 제공자 호출/시간 | 30 | 300 |
| 동시 제공자 호출 | 2 | 4 |
| 등록 세션 생성/시간 | 20 | 200 |
| 진행 중 등록 세션 | 5 | 100 |

시간 구간은 UTC 정각 단위이며 설정은 [환경변수 예시](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/.env.example)에 있다. 위 수치는 서비스에 정한 기본 운영 정책이지 ASVS·KISA가 지정한 숫자가 아니다.

대화를 [DB 세션 저장소](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/dao/aiSessions.database.js)에 보관하고 PostgreSQL advisory lock으로 같은 세션의 답변·확정·중단을 처리한다. R06에서 두 프로세스의 확정 요청은 201·409로 나뉘고 원단은 하나만 생성됐다. 중단·확정하면 활성 슬롯을 돌려준다. 확정 세션의 보관 기간과 프로세스 중단 시 업무 처리의 완전한 원자성은 별도 확장 검토 대상이다.

[제공자 타임아웃](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/ai/claudeProvider.js)은 fetch 헤더부터 response.json 본문 읽기까지 적용했다. R07은 실제 유료 모델에 장애를 주는 시험이 아니라 모의 HTTP 본문 지연 시험이다.

기존 프론트 실패는 `domain.test.js`의 SCRAP 길이 29/91 거절 기대와 `seller-fabric-api.test.js`의 길이 29 거절 기대다. 이번 변경 이전의 [프론트 로그](audit-2026-10-13/frontend-tests.txt)에서도 동일한 2개가 실패했다. 보안 테스트의 기대를 낮춘 결과가 아니다. 추가된 비밀번호·정상/오프라인 로그아웃 테스트 3개는 모두 통과했다. 기존 API 모의 서버에는 새 로그아웃 응답을 추가했다.

시험은 기존 개발 DB와 분리된 `material_loop_security_20261014_35156_test`, 전용 업로드 폴더, 가상 계정과 사진을 사용했다. 기존 운영 데이터나 실제 AI 모델을 대상으로 공격 요청을 보내지 않았다. 모든 AI 제공자 호출은 가짜 제공자·모의 HTTP이며 실제 과금은 0건이다.

코드는 기존 HEAD 이후의 미커밋 변경이다. 기준 backend HEAD는 `dd1a4333c3d64af405068b8ab35662c47854046f`, frontend HEAD는 `5144a45ea8f57f4803147dbb8b60374243967838`이며, 수정본을 이 HEAD 자체의 결과로 표시하면 안 된다. [수정 파일 SHA-256](fix-2026-10-14/source-hashes.json)과 원시 로그를 함께 보관한다.

재실행 스크립트는 [전체 검증](reproduction/security-fix-2026-10-14-verify.mjs.txt), [보안 HTTP 점검](reproduction/security-fix-2026-10-14-probe.mjs.txt), [별도 서버 프로세스](reproduction/security-fix-2026-10-14-probe-worker.mjs.txt)다. 이 스크립트는 특정 격리 `_test` DB만 사용하도록 검사하며 테스트 DB를 초기화한다. 공용·개발·운영 DB로 바꾸어 실행하지 않는다.

## 로컬 적용과 배포 조건

현재 로컬 개발 DB `material_loop_local`에 두 마이그레이션을 적용했고 `.env`의 AI_SESSION_STORE를 database로 바꿨다. 기존 회원·거래 행을 초기화하지 않았다. [적용 로그](fix-2026-10-14/local-migration.txt).

[보안 API 추가 계약과 적용 순서](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/docs/API_SECURITY_2026-10-14.md)에 4개 보안 테이블·회원 입력 길이 열, 기본 한도와 운영 순서를 정리했다. 운영에서는 마이그레이션, 모든 백엔드 인스턴스 교체, 프론트 동시 반영, 동일 JWT_SECRET·DB·사진 저장소, 업로드 프록시 우회·캐시 제거, 기존 경계값 계정 복구 준비가 필요하다. 기존 memory AI 세션은 자동 이행되지 않는다.

실제 공개 서버 주소·TLS·프록시·CDN·운영 DB 권한은 아직 검증하지 않았다. 수정된 코드와 로컬 마이그레이션을 운영 배포 완료로 발표하지 않는다.

## 남은 우선순위

F1~F4의 재현 시나리오는 개선 후 통과했고 F5도 함께 해결했다. 기존 경계값 계정 복구는 배포 조건이다. 다음 P1 작업은 xlsx 의존성 공지 처리, `/users/me` 등 개인정보 API의 no-store, 구조화 보안 사건 로그다. 사진 응답의 no-store를 추가했다고 개인정보 API 전체의 캐시 문제가 해결된 것은 아니다. P2로 남은 uuid 도달 경로·업데이트, 확정 AI 대화 보관 기간도 이전 우선순위를 유지한다.
