# 패브링 보안 기준 선정과 적용 계획

> 저장소 보관본: 아래 내용은 점검 당시의 기록이다. 이후 사용자 요청으로 보안 브랜치에 커밋·푸시하며, 로컬 경로·시험용 서명값은 공개용으로 정리했다. 원본 증거와 ZIP은 로컬에 보존한다.


기준 확인일: 2026년 10월 13일

패브링에는 **OWASP ASVS 5.0.0을 중심 점검 기준으로 두고, OWASP API Security Top 10 2023으로 API 위험을 분류하며, KISA JavaScript 시큐어코딩 가이드 2023년 개정본을 구현 참고로 연결하는 구성**을 추천한다. 검증 절차는 OWASP WSTG 4.2를 사용한다. 발표에서는 OWASP Top 10 2025로 위험을 설명하고, 개별 개선에는 정확한 ASVS 요구사항과 테스트 결과를 붙인다.

이 구성은 구매자·판매자·관리자 권한, 예약과 재고, 사진 업로드, 비공개 문의, AI 보조 등록이 있는 현재 서비스에 맞춰 선정했다. 아래 적용 범위와 우선순위는 패브링을 위한 제안이며, 표준의 전체 항목이나 인증 결과를 뜻하지 않는다.

## 적용 대상과 현재 확인 범위

| 구분 | 현재 검토 대상 |
| --- | --- |
| 프론트엔드 | React 19와 Vite, `frontend` 체크아웃 HEAD `5144a45` |
| 백엔드 | Node.js와 Express, PostgreSQL과 Sequelize, `backend-local` 체크아웃 HEAD `dd1a433` |
| 인증 | Bearer JWT, bcrypt 비밀번호 해시, 탭의 sessionStorage를 통한 토큰 보관 |
| 주요 기능 | 역할별 가입과 로그인, 매장과 원단 관리, 관리자 승인, 픽업 예약과 재고, 문의, 관심 저장, AI 보조 등록 |
| 파일 처리 | 판매자 사진 업로드, 서버의 로컬 파일 저장소, 공개 이미지 URL |
| 배포 | 팀 배포 문서상 오라클 배포 예정. OS, 웹서버, HTTPS, 프록시, DB 연결 방식은 미정 |

코드에서 보안 통제의 존재와 검토 후보를 확인한 범위다. 실제 요청으로 취약점을 재현하거나 배포 서버를 점검한 결과는 아니다. 기존 QA 문서의 기능 테스트 통과 수는 이번 보안 점검의 통과 수로 합산하지 않는다.

## 우선 적용할 네 문서

| 문서와 고정 버전 | 문서의 역할 | 패브링에서 적용할 부분 | 추천 이유 |
| --- | --- | --- | --- |
| [OWASP ASVS 5.0.0](https://owasp.org/projects/asvs) | 무엇을 충족해야 하는지 정하는 검증 요구사항 | 권한, 인증, JWT와 세션, 파일, 입력과 출력, 업무 흐름, 설정, 로깅 | 요구사항 ID별로 완료 조건과 증거를 연결할 수 있다 |
| [OWASP API Security Top 10 2023](https://api-security.owasp.org/editions/2023/en/0x11-t10/) | API 위험을 분류하는 문서 | 타인 예약과 원단 접근, 관리자 기능 접근, 민감 필드, AI 비용, 예약 자동화 | 서버 API에 역할과 소유권 경계가 많은 구조에 적합하다 |
| [KISA JavaScript 시큐어코딩 가이드 2023년 개정본](https://www.kisa.or.kr/2060204/form?cPage=1&langType=KO&postSeq=14&searchType=&searchWord=) | JavaScript 구현을 검토할 국내 참고 가이드 | React와 Node.js의 입력 처리, 안전한 출력, 데이터와 파일 처리 | 프론트와 백엔드가 모두 JavaScript이므로 언어별 참고 자료로 적합하다 |
| [OWASP WSTG 4.2](https://wstg.owasp.org/v4.2/) | 어떻게 테스트할지 설명하는 가이드 | 권한 우회, ID 변경, 로그아웃, 입력값, 업로드, 업무 흐름과 배포 설정 검증 | 개선 전후를 같은 절차로 재현하고 발표 증거로 남기기 좋다 |

ASVS는 공식 프로젝트가 안내하는 안정 버전 5.0.0을 고정한다. 요구사항은 `v5.0.0-8.2.2`처럼 버전까지 기록한다. WSTG도 `latest` 링크 대신 4.2 링크와 테스트 ID를 기록한다. API Top 10은 위험 분류이므로 개별 테스트의 충족 조건은 ASVS와 서비스 권한 정책에서 정한다.

KISA JavaScript 가이드의 게시글 등록일은 2022년 12월 30일이지만 현재 첨부파일 이름은 `Javascript_시큐어코딩_가이드(2023년_개정본).pdf`다. 발표에서 기준 판본은 첨부파일을 기준으로 적는다. [KISA 공식 게시글](https://www.kisa.or.kr/2060204/form?cPage=1&langType=KO&postSeq=14&searchType=&searchWord=).

| 문서 | 언제 사용하면 좋은가 | 이번 작업에 적용하는 방식 |

Top 10은 주요 위험을 설명하는 인식 문서다. 열 가지 이름에 대응하는 기능을 넣었다는 이유만으로 사이트 전체의 보안 검증이 완료되는 것은 아니다. 실제 완료 판정은 아래처럼 요구사항과 증거를 기준으로 한다. [OWASP Top 10 공식 설명](https://top10.owasp.org/2025/).

인프라 가이드는 적용 OS와 웹서버가 정해진 뒤 항목 번호를 매긴다. 현재 서비스에 관련된 항목을 참고하는 것이며, 기반시설 지정 여부나 법적 의무 이행을 판정하는 용도로 사용하지 않는다. 예전 판본의 항목 번호를 개정 문서에 그대로 가져오지 않는다.

KISA 가이드와 ASVS의 연결은 프로젝트에서 정한 주제별 대응표다. 기관이 공인한 일대일 대응표가 아니다. KISA의 정확한 절 제목과 페이지는 작업 담당자가 해당 첨부 PDF를 확인해 결과 기록에 추가한다.

## ASVS 적용 범위

1차에서는 권한, 인증, JWT, 세션 종료, 입력과 출력, 파일 처리와 관련된 L1 요구사항부터 점검한다. 예약 동시성, 민감 필드, 자동 호출 제한, 비밀값 관리와 보안 로그는 관련 L2 요구사항을 추가한다. 이미지 픽셀 제한처럼 서비스에 필요한 일부 L3 통제도 개별적으로 선택할 수 있다.

이는 **ASVS 요구사항을 선별 적용하는 계획**이다. 특정 레벨을 충족했다고 발표하려면 그 레벨의 전체 적용 대상과 제외 사유를 확정하고 검증해야 한다. 기존 통제가 있는 항목도 실제 요청, 응답과 저장 결과를 확인한 뒤 통과로 기록한다.

## 사이트 기능과 기준의 연결

P0는 공개 전 먼저 확인할 작업, P1은 거래 흐름과 AI 운영 전에 완료할 작업, P2는 운영 체계를 보강할 작업이다. 이 우선순위는 작업 순서이며 실제로 발견한 취약점의 심각도 등급은 별도로 판정한다.

ASVS 숫자는 모두 버전 5.0.0 기준이다. 예를 들어 SEC-02의 정식 표기는 `v5.0.0-8.2.2`다. SEC-07의 5.2.6은 L3 항목이며, 선택한 이유는 큰 이미지의 처리 비용 때문이다. KISA 가이드는 각 작업의 입력·출력·권한·파일·오류 처리 구현을 검토할 때 연결한다.

### 먼저 확인할 개선 후보

**비밀번호 문자 수와 바이트 수의 차이.** [auth.schema.js](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/validators/auth.schema.js)는 `.max(72)`로 문자열 길이를 제한하고 주석에서는 bcrypt의 72바이트 제한을 설명한다. 한글과 이모지는 문자 길이와 UTF-8 바이트 길이가 다르므로 경계값 테스트가 필요하다. OWASP는 bcrypt를 사용하는 경우 72바이트 제한을 다루도록 안내하고 신규 설계에서는 Argon2id 등도 제시한다. 변경 시 기존 해시 호환성과 비밀번호 검증 방식까지 함께 설계한다. [Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

**로그아웃 이후 토큰 폐기.** 현재 프론트의 [live-api.js](https://github.com/goduckTeam/Frontend/blob/security/p0-hardening-20261014/src/react/services/live-api.js)는 저장한 토큰을 제거하는 로그아웃을 제공한다. 복사해 둔 JWT의 재사용을 종료시키는 서버 계약은 별도로 정해야 한다. 토큰 수명만 줄이는 방식과 즉시 폐기는 서로 다른 결과를 낸다. 기준은 ASVS 7.4.1이며 테스트는 [WSTG 4.2 로그아웃 검증](https://wstg.owasp.org/v4.2/4-Web_Application_Security_Testing/06-Session_Management_Testing/06-Testing_for_Logout_Functionality/)으로 연결한다.

**AI와 업로드의 사용자별 한도.** 현재 [AI 라우트](https://github.com/goduckTeam/backEnd/blob/security/p0-hardening-20261014/src/routes/aiSessions.routes.js)에서 역할 검증을 확인했지만, 인증 라우트와 같은 호출 횟수 제한은 해당 라우트에 연결돼 있지 않다. 계정별 일일 한도, 전체 동시 처리, 저장 용량과 실패 재시도 상한을 확인한다. 비용 한도 테스트는 가짜 AI 제공자로 먼저 검증하고 실제 모델은 제한된 예산으로 별도 확인한다.

**사진 원본의 공개와 개인정보.** 썸네일은 변환하지만 원본은 업로드 버퍼를 저장한다. EXIF 위치정보 등 메타데이터 제거 여부, 판매자만 볼 초안 사진을 공개 URL로 제공할지, 원단 삭제 후 파일의 보관 정책을 정한다. 이미지를 다시 인코딩하는 개선을 선택했다면 파일 형식, 방향과 품질도 재검증한다.

**실제 프론트 응답의 보안 헤더와 운영 로그.** Express의 Helmet 설정으로 정적 프론트 HTML의 CSP가 자동 보장되지는 않는다. 배포 웹서버에서 반환하는 헤더를 따로 확인한다. 현재의 오류 출력과 별개로 로그인 실패·권한 거절·관리자 승인 같은 사건을 기록할 항목, 마스킹, 접근 권한과 보관 기간을 정한다.

이 후보들은 재현과 정책 확인을 거쳐 개선 여부를 결정한다. 기존 코드가 이미 차단하는 사례는 신규 취약점 수정으로 집계하지 않는다.

## 작업 순서와 검증 방법

1. 적용 요구사항과 자산을 정한다. 구매자 A와 B, 판매자 A와 B, 미승인 판매자, 관리자, 비로그인 상태의 권한표를 만든다. 어떤 데이터가 공개이고 비공개인지 함께 적는다.
2. 격리된 테스트 DB와 가상 데이터에서 현재 동작을 기록한다. 허용 사례와 거절 사례를 함께 확인하고 DB와 파일의 변경 여부를 비교한다.
3. 재현된 문제와 정책 공백에 기준 ID를 붙여 수정한다. 요구사항이 이미 충족된 항목은 기존 통제 검증으로 기록한다.
4. 수정 전과 같은 요청을 다시 보내고 정상 사용자 흐름도 확인한다. 인증 화면, API 응답, 저장 데이터까지 같은 커밋에서 검증한다.
5. 배포 구성이 정해지면 실제 HTTPS·프록시·CORS·DB·이미지 경로와 운영 계정을 확인한다. 서버 재시작과 여러 서버 조건이 있다면 메모리 제한의 동작도 확인한다.
6. 기준 ID, 결과, 남은 과제와 증거 경로를 확정한 뒤 발표 사례를 고른다.

기존 백엔드 테스트 중 `auth.test.js`, `rateLimit.test.js`, `images.test.js`, `reservations.test.js`, `inquiries.test.js`, `admin.test.js`, `aiSessions.test.js`를 먼저 기준과 연결한다. 프론트 테스트는 화면과 세션 동작을 보완하며 서버 권한 검증을 대신하지 않는다. 기존 파일이 존재한다는 사실은 해당 기준 전체의 통과 증거가 아니다.

도구는 목적에 맞춰 사용한다. 의존성 분석은 실제 잠금파일과 배포 실행 경로를 기준으로 수행한다. 프록시 도구나 OWASP ZAP은 테스트 환경의 HTTP 요청과 응답을 확인하는 데 사용할 수 있다. 역할별 권한, 재고 동시성, AI 비용은 서비스 시나리오와 서버 테스트로 함께 검증한다.

실제 새로 개선한 사례가 있다면 문제 재현 → 기준 → 변경 → 동일 요청 재점검으로 보여 준다. 처음부터 차단된 사례는 기존 통제 검증으로 설명한다. 위 사례들은 발표 후보이며 개선 전후 결과가 확보된 항목을 최종 선정한다.

발표 문장 예시:

> 패브링의 역할별 API와 거래 데이터를 대상으로 OWASP ASVS 5.0.0의 관련 요구사항을 선정하고, KISA JavaScript 시큐어코딩 가이드를 구현 검토에 활용했습니다. API 위험은 OWASP API Security Top 10 2023으로 분류했으며, 권한과 세션 검증에는 WSTG 4.2의 절차를 적용했습니다. 결과는 테스트 환경과 확인한 커밋을 기준으로 제시합니다.

작업 전에는 위 문장을 계획형으로 사용한다. 결과 발표에는 실제 점검 수, 발견 수, 개선 후 재점검 결과와 보류 항목을 넣는다. 적용 제외는 사유를 적고 미점검과 구분한다. 통과율을 사용할 경우 분모는 확정한 개별 요구사항 수이며, 아래의 16개 작업 묶음 수와 혼용하지 않는다.
