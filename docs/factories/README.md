# 양주시 공장등록 자료 정제

후속 DB 적재를 완료했습니다. 현재 개발 DB에는 보류했던 15건을 포함한 2,919개 업체와 원본 2,925행이 보존돼 있습니다. 공용 환경 재현과 지도 연결 설정은 [배포 가이드](DEPLOYMENT.md)를 사용합니다. 아래 100자 검사와 적재 보류 건수는 첫 정제 단계의 기존 스키마 기준 기록입니다.

백엔드 main `1bb4ef2`에 공장 테이블, 공장 목록 API 48번, 업종 분류, 엑셀 다운로드·적재 명령이 포함돼 있습니다. 프론트 main `5975a0c`의 부자재 지도는 예시 업체·예시 위치를 사용합니다. 원본 엑셀은 기존 `.gitignore`의 `data/factories/` 규칙으로 Git에서 제외됩니다.

이번 정제는 백엔드 `feature/factory-data-preparation`에서 진행합니다. 출처 기록·정제 코드·검증을 공유하고, 원본과 전체 결과는 명령으로 재현합니다. API 계약, DB 스키마와 기존 적재 명령은 이 단계에서 변경하지 않습니다.

## 원본과 재현 명령

[양주시청 공장등록현황](https://www.yangju.go.kr/www/selectBbsNttList.do?bbsNo=66&key=563)의 2026년 9월말 자료를 사용합니다. 게시일은 2026-10-01이며 글 번호는 208645, 첨부 번호는 204154입니다. 다운로드 주소·시트명·파일 크기·SHA-256을 [출처 기록](yangju-2026-09-source.json)에 고정했습니다. 이 명령은 매번 최신 월을 자동 선택하지 않습니다.

백엔드 저장소 루트에서 Node.js 24와 기존 패키지를 준비한 후 실행합니다.

```powershell
node scripts/prepare-yangju-factories.js --download
```

원본이 이미 있으면 다운로드하지 않습니다. 파일 크기·해시·XLS 서명·시트명·엑셀 제목의 기준월을 검사하고 하나라도 다르면 정제를 중단합니다. 이 명령은 `.env`나 DB 연결 모듈을 불러오지 않아 DB 접속 정보 없이 실행할 수 있습니다.

다른 위치에 원본이 있으면 다음과 같이 지정합니다.

```powershell
node scripts/prepare-yangju-factories.js --input ./source.xls --out ./data/factories/yangju-city/2026-09/prepared
```

기본 결과 폴더는 `data/factories/yangju-city/2026-09/prepared/`입니다.

| 파일 | 내용 |
| --- | --- |
| `prepared.json` | 전체 회사명·주소 그룹, 원문, 엑셀 행 번호, 식별키, 검토 사유, 현재 스키마에 맞는 적재 후보 |
| `supply-candidates.json` | 부자재 후보, 용도 확인 대상, 검색어가 있지만 제외한 항목 |
| `review.json` | 중복 그룹, 생산품 길이 초과·누락 등 검토 사항 |
| `summary.json` | 출처와 대조 건수 |
| `report.md` | 업체 목록·중복·길이 초과를 검토할 수 있는 보고서 |

원본 2,925행은 2,919그룹과 중복 추가 6행으로 대조됩니다. 부자재 분류 28+37+10+2,844도 2,919그룹과 일치합니다. 생산품 누락 3건은 현재 DB의 nullable 컬럼에 맞춰 null로 보존되며 부자재 대상으로 추정하지 않습니다.

부자재 후보 28곳은 모두 기존 스키마의 길이·중복 검사에 맞고, 주소는 26개입니다. 같은 주소에 등록된 다른 회사는 회사명을 함께 확인하여 별도 업체로 유지했습니다. 모든 좌표는 null이며 좌표 변환은 다음 단계입니다. 첫 정제 단계에서 확인한 기존 로컬 개발 DB의 공장 행은 0건이었고, 후속 적재로 2,919건이 저장됐습니다.

## 정제 기준

- NFKC로 문자 표현을 맞추고 공백을 정리합니다. 주소의 번지·필지·동·층 등은 지우지 않습니다.
- 정규화한 회사명+주소의 SHA-256으로 `sourceKey`를 만듭니다. 기준월·엑셀 행 번호·로컬 DB의 숫자 ID가 바뀌어도 같은 회사명·주소는 같은 키를 가집니다. 이 키는 공식 사업자 식별번호가 아니므로 상호·주소가 변경된 업체의 동일성은 별도로 확인해야 합니다.
- 전화번호·FAX·종업원수는 정제 결과로 복사하지 않습니다. 원본 파일은 그대로 보존합니다.
- 완전 중복은 묶고 원문 행을 모두 남깁니다. 다른 생산품을 가진 중복은 모든 문구를 보존하여 검토 대상으로 둡니다.
- 생산품을 100자로 자르지 않습니다. 이름 100자·주소 255자·생산품 100자의 기존 DB 한도를 검사하고 초과하면 적재 후보에서 보류합니다.
- 기존 API의 광범위한 업종 `category`는 그대로 기록합니다. 부자재 선별은 별도 생산품 규칙으로 수행하므로 `OTHER`·`METAL` 등으로 분류된 단추·버클 공장을 놓치지 않습니다.
- 단추·지퍼·재봉사·레이스·리본·심지·직조라벨·의류/가방/마스크용 끈은 후보로 선별합니다. 일반 끈·라벨·원사·연사·웨빙·밴드는 용도 확인 대상으로 둡니다.
- 전자/산업용 라벨·티켓, 전기 레이스웨이, 건축/가구/커튼/화장품 부자재, 가발 원사는 대상에서 제외하고 근거를 남깁니다.
- 생산품에 따른 추론이며, 소매 판매·영업 여부·협력 업체 등록을 확인한 목록은 아닙니다.

## 기존 적재기에서 확인한 사항

기존 `scripts/factorySync.js`는 `clip(..., 100)`으로 긴 생산품을 자르고, 동일 회사명·주소에서 마지막 행의 생산품을 채택합니다. 이 원본에서는 길이 초과 11건과 다른 생산품을 가진 중복 4그룹의 원문이 유실됩니다. 첫 정제에서 해당 15그룹을 보류했고, 후속 적재 명령은 이 손실 가능한 경로를 사용하지 않도록 보완했습니다.

기존 `factories:pull`은 다운로드 직후 실제 DB 적재까지 실행합니다. 자료 검토 단계에서는 위 정제 전용 명령을 사용합니다. `prepared.json`의 `importRows`는 검토용 데이터이며 현재 적재기에 자동 연결되지 않습니다.

## 공용 DB로 이어갈 작업

1. 생산품 11건의 원문을 저장할 수 있는 컬럼 변경과 충돌 중복 4그룹의 처리 규칙을 정합니다. 기존 마이그레이션을 고치지 않고 후속 마이그레이션으로 적용합니다.
2. 공용 DB에서 중복 적재를 막을 식별키·고유 제약과 자료 기준월 관리 방식을 반영합니다.
3. 먼저 부자재 후보 28곳의 서로 다른 주소 26개를 좌표 변환합니다. 용도 확인 대상 37곳은 검토 결과에 따라 포함합니다.
4. 좌표 결과를 환경별 숫자 ID 대신 `sourceKey`와 주소로 연결하고, 주소 변경 시 이전 좌표를 재사용하지 않도록 검사합니다.
5. 빈 공용 DB에서 마이그레이션·같은 원본·정제·적재 명령으로 목록이 재현되는지 확인합니다.

첫 단계에서 출처 고정과 자료 정제를 수행했고, 후속 단계에서 개발 DB 적재와 빈 DB 재현을 완료했습니다. 실제 공용 서버 접속과 적재는 배포 접속 정보가 있는 환경에서 위 배포 가이드에 따라 실행합니다.

## 검증

```powershell
node --test tests/factoryPreparation.test.js tests/factorySync.test.js
npm run lint
```

정제 전용 테스트는 DB 없이 실행됩니다. 정규화·동일/상이 생산품 중복·필수값 누락·100자 경계·부자재 오탐·기준월 오류·해시/크기 오류·원본 변조 시 출력 중단을 검사합니다.

원본을 다른 폴더에 다시 다운로드한 후 정제한 JSON 파일 4개와 보고서가 기존 결과와 바이트 단위로 같았습니다. 정제 전용·기존 적재기 테스트 13개, lint, 전체 백엔드 테스트 502개를 통과했습니다. 전체 회귀 검증은 로컬 루프백 PostgreSQL의 새 전용 `material_loop_factory_preparation_test` DB와 별도 테스트 업로드 경로에서 수행했습니다. 원본 2,925행의 회사명·주소·생산품 원문이 결과에 모두 보존됐는지도 별도로 대조했습니다.
