# 2026-10-14 보안 계약 추가사항

사용자가 승인한 P0 보안 개선을 반영한 v0.3 추가사항이다. 기존 `Material_Loop_API_명세서_v0.3.docx`는 49개 API의 이전 기준이며, 이 추가사항을 합치면 로그아웃을 포함해 50개다. 읽기용 명세와 생성된 OpenAPI에는 변경을 반영했다.

## 비밀번호와 기존 계정

가입은 8자 이상, UTF-8 72바이트 이하를 허용한다. 로그인도 72바이트를 넘으면 `400 VALIDATION_ERROR`다. 공백·대소문자를 바꾸거나 입력을 잘라 비교하지 않는다. 한글 24자는 72바이트, 이모지 18개는 72바이트다. 운영팀 계정 생성도 같은 상한을 적용한다.

신규 가입·운영팀 생성은 `users.password_byte_length`에 검증한 원래 길이를 기록한다. 비밀번호와 해시는 응답에 넣지 않는다. 기존 해시는 원래 입력 길이를 복구할 수 없어 이 값이 NULL로 남는다. 기존 계정에서 72바이트를 입력하면, 잘린 긴 비밀번호의 접두사인지 구별할 수 없으므로 `401 LOGIN_FAILED`로 거절한다. 기존 계정의 72바이트 미만 비밀번호와 새로 검증해 생성한 정확히 72바이트 비밀번호는 유지한다.

기존 경계값 계정은 본인 확인을 거쳐 새 비밀번호로 재설정해야 한다. 현재 API에는 비밀번호 재설정 경로가 없으므로, 실제 사용자가 있다면 검증된 복구 절차를 준비한 후 배포한다. 기존 값을 임의로 72로 채우거나 해시를 잘라 변경하면 우회가 다시 생길 수 있다. 모든 Unicode 비밀번호 64자를 지원하는 ASVS 6.2.9의 전체 충족은 이 bcrypt 방안으로 주장하지 않는다. 이를 목표로 할 때는 Argon2id 등 긴 입력을 처리하는 해시와 계정 이행을 추가한다.

## 로그아웃

`POST /api/v1/auth/logout`, `Authorization: Bearer <현재 토큰>`, 본문 없음. 성공은 `200 {"success":true,"data":null}`, 없거나 잘못되었거나 만료·폐기된 토큰은 `401 UNAUTHORIZED`다.

서버는 토큰의 SHA-256 지문과 만료 시각을 DB에 저장하고 보호 요청마다 조회한다. 같은 토큰을 다른 프로세스나 재시작한 서버에 보내도 거절한다. 새 로그인에는 독립적인 `jti`를 발급한다. 현재 토큰을 폐기하며 다른 기기의 토큰까지 모두 종료하는 API는 아니다.

프론트는 먼저 로컬 계정 정보와 저장한 토큰을 비운 후 복사해 둔 토큰으로 서버 폐기를 요청한다. 서버 연결 실패 시 로컬 로그아웃은 수행하되, 서버 폐기가 확인되지 않았다는 안내를 보여 준다. 401은 이미 사용할 수 없는 토큰으로 취급한다.

## 원단 사진

`/uploads` 디렉터리를 직접 정적 공개하지 않는다. 원본과 썸네일은 매 요청에서 삭제 여부와 DB에 연결된 사진인지 검사한다.

| 상태/접근 | 결과 |
| --- | --- |
| 삭제되지 않은 POSTED 원단의 연결된 사진 | 공개 조회 허용. 공개 API는 서명 없는 URL을 반환 |
| 비공개 원단 + 소유 판매자/ADMIN의 Bearer 토큰 | 조회 허용 |
| 비공개 원단 + 권한 있는 API가 발급한 유효한 사진 서명 URL | 최대 300초 조회 허용 |
| 비공개 원단 + 서명 없는 URL/다른 판매자/서명 변조·만료 | 404 |
| 삭제된 원단/삭제된 사진/등록되지 않은 경로 | 서명과 역할에 관계없이 404 |

권한 있는 판매자·운영팀·본인 예약 API만 비공개 사진 링크를 발급한다. 관심 목록에서는 POSTED가 아니거나 삭제된 원단의 썸네일을 null로 돌려준다. 예약 당사자는 자신에게 공개된 예약 기록의 사진 링크를 받을 수 있다. 공개 URL에는 비공개 조회 권한이 없어 게시를 내리면 즉시 거절한다.

서명 URL은 제한된 기간에 사진을 읽을 수 있는 전달 가능한 권한이다. URL을 받은 사람은 300초 동안 사용할 수 있으며 로그아웃 토큰과 별도로 만료된다. 프록시 접근 로그의 쿼리 문자열을 마스킹하고, 만료 후에는 권한 있는 API에서 다시 조회한다. `Cache-Control: no-store`, `Referrer-Policy: no-referrer`를 적용한다. 이미 내려받은 사본은 서버에서 회수할 수 없다.

새 업로드는 재인코딩해 EXIF 등의 메타데이터를 제거한다. 기존 저장 파일에 메타데이터가 남아 있어도 다운로드 응답은 이를 제거해 전송한다. 기존 디스크 파일과 백업 자체의 정리는 별도 보관 정책 대상이다. JPG·PNG·WebP, 5MB 업로드 한도, 4천만 픽셀 한도는 유지한다.

## 전체 API 요청 횟수 제한

`/api/v1` 아래 모든 API와 `/uploads` 사진 조회는 IP별 한도를 공유한다. 기본은 60초에 300회이며 `API_RATE_LIMIT_WINDOW_MS`·`API_RATE_LIMIT_MAX_REQUESTS`의 양의 정수로 조정한다. 성공·입력 오류·인증 실패·404 모두 사용량에 포함한다. 경로·query·메서드·로그인 계정을 바꿔도 같은 IP의 카운터를 사용한다. 브라우저 CORS preflight(`OPTIONS`)와 Swagger 문서 조회는 제외한다.

미들웨어는 JSON 파싱·인증·라우트·파일 처리 앞에서 실행한다. 초과 시 본문 파싱, DB 조회/변경, 파일 처리와 AI 호출 전에 기존 `429 TOO_MANY_REQUESTS` 형식으로 거절한다. 응답은 `Cache-Control: no-store`이며 `RateLimit`·`RateLimit-Policy`와 초과 시 `Retry-After`를 제공한다. CORS에서도 이 헤더를 노출한다. 가입·로그인은 별도의 공통 15분 20회 제한을 함께 적용하고 `auth` 정책으로 안내한다. AI의 사용자·전체 호출/세션 한도는 DB에서 별도로 유지한다. [express-rate-limit 설정](https://express-rate-limit.mintlify.app/reference/configuration).

기본은 직접 연결한 주소를 사용하고 전달 헤더를 신뢰하지 않는다. 실제 프록시를 사용할 때만 `TRUSTED_PROXY_CIDRS`에 프록시의 IP·CIDR을 쉼표로 지정한다. `true`·숫자 홉 수·`/0`·잘못된 주소는 시작을 거절한다. 프록시는 전달 헤더를 올바르게 덮어쓰거나 연결 주소를 추가해야 하며, 백엔드에 직접 접근할 수 있는 네트워크 경로와 프록시 설정도 검토해야 한다. 지정되지 않은 중간 주소 앞의 위조 주소는 신뢰하지 않는다. IPv6는 `/56`으로 묶어 동일 대역 안의 주소 교체를 제한한다. [Express의 프록시 신뢰 설정](https://expressjs.com/en/guide/behind-proxies/).

기본 카운터는 `express-rate-limit`의 MemoryStore로 서버 프로세스별 관리하며 재시작하면 초기화된다. 여러 인스턴스를 운영할 때 총량까지 합산하려면 프록시/게이트웨이의 공통 제한이나 별도의 공유 카운터 저장소가 필요하다. 동일한 공인 IP를 공유하는 사용자도 기본 한도를 공유하므로 실제 트래픽에 맞춰 수치를 조정한다. 이번 작업은 원격 프록시·DB·배포 설정을 변경하지 않았다. 로컬 회귀 테스트는 낮은 한도로 모든 라우트의 차단 순서·동시 요청·창 만료·IPv4/IPv6·프록시 위조·기존 인증/AI 한도를 검사한다. 일반 테스트는 같은 루프백 IP로 많은 시나리오를 실행하므로 `tests/setup.js`에서 별도 지정이 없을 때 10,000회로 넓히며, 운영 기본값 300회는 별도 자식 프로세스로 확인한다.

## AI 자원 제한

사진 분석과 대화 답변의 실제 제공자 호출에 공통 한도를 적용한다. 유료 제공자를 부르기 전에 DB 트랜잭션으로 사용량과 활성 슬롯을 예약한다. 여러 서버가 같은 DB를 사용하면 같은 한도를 공유한다. 초과 시 `429 TOO_MANY_REQUESTS`이며 재시도하지 않는다.

| 설정 | 기본값 | 의미 |
| --- | ---: | --- |
| AI_USER_CALLS_PER_HOUR | 30 | 계정별 제공자 호출/시간 |
| AI_GLOBAL_CALLS_PER_HOUR | 300 | 서비스 전체 제공자 호출/시간 |
| AI_USER_CONCURRENT_CALLS | 2 | 계정별 동시 제공자 호출 |
| AI_GLOBAL_CONCURRENT_CALLS | 4 | 서비스 전체 동시 제공자 호출 |
| AI_USER_SESSIONS_PER_HOUR | 20 | 계정별 신규 등록 세션/시간 |
| AI_GLOBAL_SESSIONS_PER_HOUR | 200 | 전체 신규 등록 세션/시간 |
| AI_USER_ACTIVE_SESSIONS | 5 | 계정별 진행 중 세션 |
| AI_GLOBAL_ACTIVE_SESSIONS | 100 | 전체 진행 중 세션 |
| AI_TIMEOUT_MS | 15000 | 제공자 요청의 헤더·본문 읽기 제한(ms) |

시간당 한도는 UTC 정각부터 다음 정각까지의 고정 구간이다. 제공자 실패와 허용된 재시도도 각각 호출 사용량에 포함되며, 이미 소비한 비용은 환급하지 않는다. 기존 최대 2회 제공자 시도는 유지한다. 버튼 선택 답변과 세션 조회는 제공자를 호출하지 않는다. 동시 슬롯은 성공·실패 후 해제하며 프로세스 중단 시 타임아웃+5초 뒤 만료한다. 세션은 마지막 갱신 후 24시간 동안 활성이고 확정·중단 시 슬롯을 해제한다.

개발·운영의 기본 세션 저장소는 `AI_SESSION_STORE=database`. 운영에서는 memory 저장소를 거절한다. DB 대화와 PostgreSQL advisory lock으로 프로세스가 달라도 같은 세션의 조회·답변·확정·중단을 순서대로 처리한다. 호출 수 제한은 비용 상한을 위한 방어이며 공급자 계정의 금액별 예산 제한을 대신하지 않는다.

진행 중·중단 세션은 마지막 갱신 후 24시간이 되면 삭제하며 해당 세션의 활성 슬롯도 같은 트랜잭션에서 해제한다. 확정 세션은 기록·원단 연결·판매자가 확정한 최종 등록값·호출 사용량을 보존하고, 확정 시 마지막 갱신 후 30일이 되면 대화·AI 초안·임시 입력 상태를 비운다. 등록된 원단 테이블은 이 정리 작업으로 변경하거나 삭제하지 않는다. 오래된 확정 세션 조회에는 빈 `messages`와 `ai_draft`를 반환하며 응답 필드와 소유권 검사는 유지한다.

공식 서버 진입점(`src/server.js`)은 시작 시점과 매 60초마다 최대 100개 후보를 정리한다. 세션 조회에서도 해당 세션의 만료·보관 정책을 검사한다. 확정·중단 상태 저장 직후 프로세스가 종료되어 남은 활성 슬롯도 기록과 함께 확인해 회수한다. 정리기는 답변·확정이 진행 중인 세션 잠금을 건너뛰고, 잠금을 얻은 뒤 최신 상태와 갱신 시각을 다시 확인한다. 서버 종료 시 정리 작업이 끝난 뒤 DB 연결을 닫는다. 기존 `ai_sessions`와 `ai_usage_leases` 테이블을 사용하며 이번 변경에는 새 마이그레이션이 없다.

## AI 입력과 프롬프트 인젝션

`p3` 프롬프트는 추출·사진 분석·상품 소개·도안 생성 모두 고정된 시스템 지침을 사용한다. 제작 대상과 메모를 시스템 문자열에 합치지 않고 사용자 메시지의 `untrusted_data` JSON으로 전달한다. 따옴표·개행과 태그 경계를 이스케이프하며, 이전 AI 초안도 같은 데이터로 취급한다. 상품 소개의 소재·치수·촉감·메모는 각각 별도 필드로 전달해 메모 속 가짜 항목 이름과 섞지 않는다. 초안·상품·원단에서는 작업에 필요한 필드만 제공자 프롬프트에 포함한다.

시스템 규칙은 역할 사칭, 지침·응답 형식 변경, 비밀·외부 접속·자동 등록 요구와 사진 속 글자(OCR)의 명령을 따르지 않도록 명시한다. 사진과 사용자 내용은 user 역할에만 전달하며 AI에 DB·코드 실행이나 외부 도구 권한을 주지 않는다. 기존 서버의 출력 필드·enum·길이·치수 검사와 판매자의 확정 절차를 유지한다. 소개의 판매자 확인 메모도 최대 1,000자로 제한한다. AI 응답은 소유권·역할·세션 확정·도안 저장 여부를 결정하지 않는다.

이는 공격 가능성을 줄이는 여러 방어 중 하나이며, JSON 인코딩이나 지침만으로 모델의 의미 해석을 완전히 통제하지는 못한다. 로컬 가짜 응답 테스트는 메시지 역할·데이터 경계와 조작된 출력의 서버 처리를 검증한다. 실제 모델의 공격 지시 준수율이나 생성 문장의 사실 정확도를 검증한 결과는 아니다. 설계 근거: [OpenAI의 프롬프트 인젝션 방어 지침](https://developers.openai.com/api/docs/guides/agent-builder-safety).

## CI 의존성 취약점 검사

CI의 `dependency-audit` 작업은 Node.js 24에서 `npm audit --package-lock-only --include=dev --audit-level=low --registry=https://registry.npmjs.org`를 실행한다. 런타임·개발 의존성을 잠금 파일 기준으로 검사하고 `low` 이상이면 실패한다. 레지스트리 연결 실패도 검사 성공으로 취급하지 않는다. 기존 lint·테스트 작업과 독립적이며 DB 서비스·비밀값·환경 파일 없이 실행한다. 검사 중 패키지 설치·자동 수정은 하지 않는다.

`main`·`deploy/test` 대상 PR과 `main`·`deploy/test`·`deploy/chaeeun/review` 푸시에 실행한다. 현재 알려진 취약점도 예외로 숨기지 않으므로 미해결 의존성이 있으면 CI가 실패한다. 이 검사는 npm 레지스트리가 제공하는 공개 취약점 정보에 대한 검사이며 모든 취약점을 탐지한다는 뜻은 아니다. 실패 기준과 보고서 출력의 관계는 [npm audit 공식 문서](https://docs.npmjs.com/cli/commands/npm-audit/)를 따른다.

## Sequelize의 uuid 의존성

Sequelize의 안정판 `6.37.8`은 `uuid ^8.3.2`를 요구한다. `GHSA-w5hq-g745-h8pq`의 버퍼 경계 검사 누락을 해결하기 위해 루트 `package.json`의 `overrides.sequelize.uuid`를 보안 패치 버전 `11.1.1`로 고정하고 잠금 파일을 갱신한다. Sequelize 버전과 다른 의존성의 잠금 항목은 유지한다. 이는 경고를 제외하는 설정이 아니라 실제 하위 패키지 교체다.

`uuid 11.1.1`은 CommonJS를 지원하므로 Sequelize 내부의 `require('uuid').v1/v4` 호출을 유지할 수 있다. 로컬 회귀 테스트는 Sequelize가 실제 찾는 모듈로 UUID 기본값·쿼리/트랜잭션 식별자를 확인하고, PostgreSQL 커밋·롤백·중첩 savepoint를 검사한다. `v3/v5/v6`의 작은 버퍼·음수·범위 밖 오프셋은 `RangeError`를 내며 버퍼를 변경하지 않아야 한다. 유효한 버퍼의 정상 쓰기도 함께 검사한다.

팀원과 배포 환경에서는 갱신된 루트 `package.json`과 `package-lock.json`을 함께 사용해 `npm ci`로 설치하고 백엔드를 재시작한다. 앞으로 Sequelize나 uuid를 갱신할 때는 override 필요 여부와 CommonJS·UUID·트랜잭션 호환성을 다시 확인한다. 근거: [uuid 보안 공지](https://github.com/uuidjs/uuid/security/advisories/GHSA-w5hq-g745-h8pq), [npm overrides](https://docs.npmjs.com/files/package.json/#overrides).

## 요청 본문의 허용 필드

모든 API의 JSON 본문 객체는 `z.strictObject`로 선언한다. 가입·로그인·회원/매장 수정·원단 등록/수정·예약·문의·관심·AI 답변/소개/도안과 확정에 동일하게 적용한다. 원단의 `detail`과 AI 소개의 `images` 배열 안 각 객체도 검사한다. 정상 필드와 추가 필드를 함께 보내도 요청 전체를 `400 VALIDATION_ERROR`로 거절하며 DB 변경이나 AI 호출에 진입하지 않는다. 기존 세 곳의 엄격한 수정 스키마도 유지한다.

공통 `validate`는 본문 스키마가 없는 API에 생략 또는 빈 객체만 허용한다. 승인·취소·수령·삭제·AI 시작/중단·로그아웃과 본문 없는 읽기 API도 적용한다. 회원/매장 조회·헬스·엑셀 다운로드 및 업로드 등 검증이 없던 라우트에도 미들웨어를 연결한다. 파일은 기존 multipart `file` 필드로 받으며 원단 사진 업로드의 텍스트 필드는 `image_type`만 허용한다. AI 사진과 엑셀 업로드는 추가 텍스트 필드를 받지 않는다. 파서가 읽지 않는 text/plain·form-urlencoded 등의 본문을 "본문 없음"으로 통과시키지도 않는다.

오류 응답은 기존 `{success:false,error:{code,message,details:[{field,message}]}}` 형식이다. 추가 필드 오류의 `field`는 객체 위치(`body`, `detail`, `images.1` 등)이며 메시지에 알 수 없는 키를 알린다. 제출한 필드 값은 이 오류에 포함하지 않는다. 정상 값의 trim·기본값·null/선택 필드·본문 생략 처리, 인증/역할 검사 순서와 URL params/query의 기존 처리는 유지한다. 새 본문 객체나 중첩 객체를 추가할 때도 strictObject를 사용하고 입력 검증을 라우트에 연결한다. [Zod의 엄격한 객체 검사](https://zod.dev/api#zstrictobject).

## 활성 예약의 DB 중복 방지

`20261014100000-active-reservation-unique.cjs`는 `reservations_buyer_fabric_active_unique` 부분 UNIQUE 인덱스를 만든다. 키는 `(buyer_id, fabric_id)`이고 조건은 `status IN ('REQUESTED', 'ACCEPTED')`다. 같은 구매자가 같은 원단에 활성 예약을 두 건 만들 수 없다. 서로 다른 구매자의 예약, 같은 구매자의 다른 원단 예약과 `REJECTED`·`CANCELED`·`PICKED_UP` 이력은 허용한다. 예약이 종료되면 다시 예약할 수 있다. 원단 행 잠금과 기존 서비스의 중복·재고 검사는 유지한다. [PostgreSQL 부분 인덱스](https://www.postgresql.org/docs/17/indexes-partial.html).

DB가 해당 인덱스의 `23505` 충돌을 반환하면 예약 생성 트랜잭션을 롤백한 뒤 기존 `409 DUPLICATE_RESERVATION`으로 응답한다. 다른 UNIQUE 오류나 DB 오류를 이 응답으로 바꾸지 않는다. 모델에도 같은 인덱스 정의를 선언하지만 실제 적용은 마이그레이션으로 수행한다.

적용 전 동일 조건으로 기존 활성 중복을 검사한다. 중복이 있으면 오류로 중단하고 예약을 삭제하거나 상태를 변경하지 않는다. 예약 담당자가 기록을 검토해 처리한 뒤 재시도해야 한다. 검사와 인덱스 생성을 한 트랜잭션에서 수행하고, 검사부터 `SHARE` 잠금으로 새 쓰기를 막는다. 생성 실패는 전체 롤백된다. `down`은 이 인덱스만 제거하며 예약 데이터는 유지한다.

일반 인덱스 생성 방식을 사용하므로 적용 중 예약 테이블의 쓰기는 잠시 대기한다. 각 문장의 `statement_timeout`은 60초, 잠금 획득의 `lock_timeout`은 5초로 제한하고 트랜잭션 종료 시 원래 설정으로 돌아간다. 예약 트래픽이 적은 시간에 적용하고 잠금·시간 초과로 실패하면 트래픽과 테이블 크기를 확인한 뒤 재시도한다. 이번 검증에서는 별도 로컬 `_test` DB에만 적용했다. 개발·원격 DB 적용이나 운영 중복 데이터 정리는 수행하지 않았다. [PostgreSQL 인덱스 생성과 동시성](https://www.postgresql.org/docs/17/sql-createindex.html).

## 구조화된 보안 로그

개발·운영 서버는 보안 사건을 stdout에 JSON 한 줄로 출력한다. 고정된 `schema_version`, UTC `timestamp`, `level`, `event`, `service`, `environment`, `pid`를 사용한다. API·사진 요청은 서버가 새로 만든 UUID를 `X-Request-Id`로 응답하며 CORS에서도 노출한다. 클라이언트가 보낸 요청 ID를 신뢰하지 않는다. 요청 로그에는 메서드·선언된 라우트 템플릿·HTTP 상태·처리 시간과 확인된 사용자 ID/역할을 더한다. 동시 요청은 AsyncLocalStorage로 분리한다.

로그인 성공·실패, 가입·로그아웃, 401·403, 입력 거절, API·인증·AI 한도 초과, 사진 접근 거절과 서버 오류를 기록한다. 관리자 작업·파일 업로드·엑셀 다운로드 성공도 기록한다. 응답 완료 또는 연결 중단은 요청당 한 번 기록하며, AI 제공자·세션 정리·잠금 연결·사진 삭제 실패는 별도의 진단 이벤트다. 요청 안의 진단은 같은 요청 ID를 사용한다. 한도 로그의 `limit_scope`는 `api`·`auth`·`ai_call`·`ai_session`을 구분한다. 권한 거절의 사용자 역할은 검증한 DB 회원에서 가져오며 실패한 로그인이나 미검증 JWT를 실제 사용자로 기록하지 않는다.

비밀번호·비밀번호 해시·JWT·Authorization·Cookie·이메일·전화번호·요청/응답 본문·URL query·경로 파라미터·파일명·사진·서명·문의/AI 원문·SQL·접속 정보·원시 오류 메시지/스택은 기록하지 않는다. 오류 종류·코드·이벤트·작업 이름 등 허용한 값만 받는다. 미등록 경로는 `/api/v1/[unmatched]`, 사진 경로는 `/uploads/[file]`로 남긴다. IP는 실행 중 생성한 전용 랜덤 키로 HMAC 가명 처리하고 IPv6 /56 및 IPv4-mapped 표현을 정규화한다. 재시작/인스턴스가 다르면 IP 가명도 달라져 그 값을 통한 인스턴스 간 추적은 제공하지 않는다. 내부 사용자 ID도 개인정보와 연결 가능한 값이므로 로그 접근을 제한해야 한다.

stdout 백프레셔 중에는 개별 기록을 대기열에 쌓지 않고 누락 건수만 보관한다. 출력이 회복되면 `logging.dropped`로 누락 건수를 알린다. 출력 예외는 요청의 인증·토큰 발급·DB 처리 결과를 바꾸지 않는다. 테스트 기본 로그 출력은 끄며, 로그 회귀 테스트는 같은 JSON 수집기를 명시적으로 연결해 민감정보 제외·주입·상관관계·출력 실패를 검사한다. [OWASP 로그 가이드](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)의 최소 정보·비밀값 제외·주입 방어·출력 실패 처리를 참고했다. 모든 OWASP 항목 충족을 뜻하지 않는다.

로그 파일을 공개 업로드 폴더나 DB에 만들지 않는다. 실제 운영 stdout 수집·접근 권한·보관 기간·회전·변조 방지·누락 경보 설정은 배포 환경의 별도 작업이다. 이번 작업에서는 원격 로그 저장소와 DB에 접속하거나 설정을 변경하지 않았다.

## 개인·인증 응답의 캐시 방지

`/api/v1`과 접근 검사를 거치는 `/uploads`의 모든 응답에 `Cache-Control: no-store`, `Pragma: no-cache`, `Expires: 0`을 적용한다. 공개 URL도 로그인 여부에 따라 정보가 달라질 수 있고 새 API의 누락을 피하기 위해 익명 API 응답에도 같은 정책을 쓴다. 공개 프론트 빌드의 JS·CSS 등 정적 자원에는 적용하지 않는다. 서버의 JSON·버퍼 응답에는 ETag를 생성하지 않는다.

미들웨어는 CORS·요청 제한·본문 파싱·인증·라우팅보다 먼저 실행한다. 가입·로그인 토큰·로그아웃·사용자·예약·문의·관심·판매자 매장·관리자·AI 세션·엑셀 다운로드의 성공 응답뿐 아니라 입력 오류, 잘못된 JSON, 401·403·404·429·500과 OPTIONS/HEAD도 보호한다. 기존 사진의 접근 검사와 파일 응답 정책은 유지한다. 프론트 HTTP 클라이언트의 기존 `cache: no-store`와 인증 전환 시 데이터 무효화는 서버 정책을 대체하지 않는다.

로컬 전용 `_test` DB에서 회귀 테스트 7건으로 정상·실패 응답과 계정 전환, 이전 캐시 조건부 헤더에 대한 새 JSON 응답을 확인했다. 운영 프록시/CDN의 캐시 우선 규칙·헤더 덮어쓰기 여부와 실제 브라우저 뒤로 가기·로그아웃 경로는 운영 구성에서 별도로 확인해야 한다. 원격 DB·프록시에 접속하거나 설정을 변경하지 않았다.

## 적용 순서

1. DB를 백업하고 `npm run migrate`로 새 마이그레이션을 적용한다. 보안 상태·비밀번호 입력 길이 마이그레이션과 `20261014100000-active-reservation-unique.cjs`도 포함된다. 기존 회원의 입력 길이를 자동 추정하지 않으며, 활성 예약 중복이 있으면 위 정책에 따라 적용을 중단한다.
2. `AI_SESSION_STORE=database`로 설정하고 모든 백엔드 인스턴스를 함께 교체한다. 이전 인스턴스가 남으면 토큰 폐기와 한도를 무시할 수 있다. 기존 memory AI 세션은 이행되지 않으므로 진행 중 등록을 마치거나 새 세션으로 시작한다.
3. 프론트를 함께 배포해 새 로그아웃 계약을 연결한다. 오래된 프론트는 서버 폐기를 요청하지 않는다.
4. 프록시/CDN이 `/uploads`를 정적 폴더로 직접 제공하거나 캐시하지 않도록 설정한다. 여러 백엔드라면 동일한 JWT_SECRET·DB·사진 저장소를 사용한다. HTTPS와 실제 운영 프록시 검증은 별도로 수행한다.
5. 실제 기존 경계값 계정의 복구 방안을 준비하고, 로그아웃 재사용·사진 삭제·429·재시작 시나리오를 운영과 같은 구성에서 확인한다.

마이그레이션을 되돌리거나 이전 서버로 복귀하면 보안 통제가 사라지므로 정상 검증을 마친 뒤 배포한다. 코드의 테스트 결과는 실제 운영 배포가 완료됐다는 뜻이 아니다.
