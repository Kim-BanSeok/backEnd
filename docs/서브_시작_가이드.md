# 서브 개발자 시작 가이드

처음 합류한 사람을 위한 안내입니다. **위에서부터 순서대로** 읽고 따라 하세요.
이 문서는 "어떻게 일하는가"를 다룹니다. 설치와 실행은 `README.md`, git 명령어와 PR 규칙은 `CONTRIBUTING.md`, AI가 지켜야 할 규칙은 `CLAUDE.md` 에 있습니다.

## 0. 먼저 알아 둘 것

- 이 프로젝트는 **API 명세서(`docs/Material_Loop_API_명세서_v0.3.docx`)가 정답**입니다. 경로, 필드 이름, 오류 코드를 내 마음대로 바꾸면 프론트엔드가 깨집니다.
- 나는 **작은 기능을 하나씩** 맡습니다. 내 담당은 `docs/담당표.md` 의 "서브" 표입니다.
- 어려운 부분(재고 계산, 동시성, AI)은 리더가 맡습니다. 내가 모르는 부분은 **추측해서 만들지 말고 물어보세요.** 물어보는 것이 일을 빠르게 합니다.
- Node, SQL 을 몰라도 됩니다. 이미 만들어진 **회원 API 를 보고 따라 하는 방식**으로 진행합니다. 직접 SQL 을 쓰지 않습니다.

## 1. 시작하는 순서 (한 번만)

1. `README.md` 의 "처음 시작하기"를 끝까지 따라 합니다. `npm test` 가 **전부 통과**하면 성공입니다. 운영팀 계정(`npm run db:seed`)은 리더가 알려 주는 값을 `.env` 의 `ADMIN_EMAIL`, `ADMIN_PASSWORD` 에 적고 실행하면 만들어집니다. (운영 API 를 직접 눌러 볼 때만 필요해요)
2. 서버를 켜고(`npm run dev`) 브라우저에서 <http://localhost:3000/api/v1/health> 가 보이는지 확인합니다.
3. `npm run dev` 를 켠 채로 <http://localhost:3000/api-docs> 를 열어 봅니다. 내가 맡을 API 의 요청·응답 모양이 그림처럼 보입니다. (Authorize 에 로그인 토큰을 넣으면 직접 호출도 해 볼 수 있어요)
4. 아래 파일을 **읽기만** 합니다. (고치지 않아요) 어떤 모양으로 코드를 쓰는지 익히는 시간입니다.
   - `src/routes/users.routes.js` → `src/controllers/users.controller.js` → `src/services/users.service.js` → `src/dao/users.dao.js`
   - `src/validators/users.schema.js`
   - `tests/auth.test.js`
5. 리더에게 "환경 설정 끝났어요"라고 알립니다. 첫 담당 기능을 확인받습니다.

> 막히면 30분 이상 혼자 붙잡고 있지 마세요. 오류 메시지 전체를 복사해서 리더에게 보내면 됩니다.

## 2. API 하나를 만드는 순서

예: 도안 목록 조회(22번)

| 단계 | 할 일 | 파일 |
|---|---|---|
| ① 명세서 읽기 | 22번의 URL, 권한, 요청 항목, 응답 예시, 처리 규칙, 오류 코드를 읽습니다 | `docs/API_명세서_v0.3.md` (또는 docx) |
| ② 입력 검사 | 요청으로 들어오는 값의 **형식**을 검사합니다 | `src/validators/patterns.schema.js` |
| ③ DB 접근 | 모델로 데이터를 읽고 씁니다. 없으면 `null` 을 돌려줍니다 | `src/dao/patterns.dao.js` |
| ④ 업무 규칙 | "안 된다"는 판단(`throw fail('NOT_FOUND')`)과 응답 모양 변환 | `src/services/patterns.service.js` |
| ⑤ 요청 연결 | `req` 에서 값을 꺼내 service 를 부르고 `ok(res, data)` 로 응답 | `src/controllers/patterns.controller.js` |
| ⑥ 주소 연결 | URL, 권한, 입력 검사를 붙입니다 | `src/routes/patterns.routes.js` |
| ⑦ 등록 | `src/routes/index.js` 에 **한 줄만** 추가합니다 | `src/routes/index.js` |
| ⑧ 테스트 | 성공, 권한 없음, 입력 오류, 상태 오류 4가지 | `tests/patterns.test.js` |
| ⑨ 확인 | `npm run lint` 와 `npm test` 가 통과해야 합니다 | |

**순서를 지키세요.** 아래(dao)부터 위(routes)로 만들면 각 단계를 바로 시험해 볼 수 있습니다.

### 자주 하는 실수

| 실수 | 올바른 방법 |
|---|---|
| 응답에 `pattern_id` 를 그대로 넣음 | 식별자는 **camelCase** → `patternId`. service 에서 응답 모양으로 변환 |
| 모델 객체를 그대로 응답 | 명세서에 있는 항목만 골라서 응답. `password_hash`, `deleted_at` 등은 절대 넣지 않음 |
| controller 에 `if (...) 오류` 규칙을 씀 | 규칙은 **service 에만** |
| 새 오류 코드를 만듦 | 명세서 3장에 있는 코드만 사용. 없으면 리더에게 요청 |
| 날짜를 `new Date()` 그대로 응답 | `toKstIso(date)` 로 변환 |
| 문자열("SELLER")을 직접 씀 | `src/utils/codes.js` 의 목록을 사용 |
| 테스트를 성공 한 개만 씀 | 4가지: 성공 / 권한 없음 / 입력 오류 / 상태 오류 |

## 3. AI 에게 일 시키는 방법

AI(Claude 등)는 서브의 가장 큰 도구입니다. 하지만 **무엇을 시키는지가 결과의 90%** 를 결정합니다.

### 3-1. 기본 원칙

1. **프로젝트 폴더에서 AI 를 실행하세요.** 프로젝트 루트의 `CLAUDE.md` 를 AI 가 자동으로 읽어서 폴더 규칙과 금지 사항을 압니다. (다른 폴더에서 실행하면 이 규칙이 적용되지 않아요)
2. **한 번에 API 1~3개만** 시킵니다. "전부 만들어 줘"는 결과를 검토할 수 없어서 위험합니다.
3. **번호를 지정합니다.** "도안 API 만들어 줘" 대신 "명세서 22번". 번호가 있으면 AI 가 명세서의 정확한 부분을 찾습니다.
4. **기준 예시를 알려 줍니다.** "회원 API(`users`)와 같은 모양으로"라고 하면 구조가 일정해집니다.
5. **범위를 제한합니다.** 어떤 파일을 만들고 어떤 파일은 건드리지 않는지 적습니다.
6. **끝났다는 기준을 줍니다.** "`npm run lint` 와 `npm test` 가 통과해야 끝"
7. **AI 의 말을 그대로 믿지 않습니다.** "통과했어요"라고 해도 내가 직접 `npm test` 를 실행해 봅니다.

### 3-2. 프롬프트 템플릿 (복사해서 빈칸만 채우세요)

**① 새 API 만들기**
```

- 명세서: docs/API_명세서_v0.3.md 의 [번호]번 항목
  (경로, 권한, 요청 항목, 응답 예시, 처리 규칙, 오류 코드를 명세서 그대로 지켜 줘)
- 기준 예시: 회원 API (src/routes/users.routes.js 부터 src/dao/users.dao.js 까지)와 같은 구조와 스타일
- 만들 파일: validators, dao, services, controllers, routes, tests/[기능].test.js

명세서에 없거나 불확실한 것은 추측하지 말고 먼저 질문해 줘.

### 3-4. AI 가 만든 결과 확인하는 법 (PR 올리기 전 5분)

1. `git status` — **내가 만들기로 한 파일만** 바뀌었나요? 모르는 파일이 있으면 AI 가 건드린 것입니다.
2. `git diff --stat` — 변경된 파일과 줄 수를 봅니다. `models/`, `migrations/`, `package.json`, `src/middlewares/` 가 있으면 **되돌립니다.** (`git restore 파일경로`)
3. `npm run lint` 와 `npm test` 를 **내가 직접** 실행합니다.
4. 응답 필드 이름을 명세서 응답 예시와 **눈으로** 비교합니다. (가장 자주 틀립니다)
5. 내가 이해하지 못하는 코드가 있으면 3-2 ③ 프롬프트로 설명을 듣습니다. **이해하지 못한 코드는 올리지 않습니다.**

## 4. 리더의 코드와 겹치지 않게 하는 방법

두 사람이 같은 파일을 동시에 고치면 충돌이 납니다. 아래 규칙만 지켜도 대부분 피할 수 있습니다.

### 4-1. 가장 중요한 5가지
1. **내 담당 기능의 파일만** 만들고 고칩니다. (`docs/담당표.md`)
2. **`git add .` 를 쓰지 않습니다.** `git add src/dao/patterns.dao.js` 처럼 파일을 지정하거나, `git add src tests` 로 폴더만 지정합니다. 그전에 `git status` 로 확인합니다.
3. **브랜치는 항상 최신 `main` 에서** 시작합니다. (`git switch main` → `git pull` → `git switch -c feature/...`)
4. **작업 전과 PR 올리기 전에 `main` 을 가져옵니다.** (`git fetch origin` → `git merge origin/main`)
5. **PR 은 작게, 자주.** API 1~3개마다 올립니다. 오래 가지고 있을수록 충돌이 커집니다.

### 4-2. 같이 쓰는 파일 (조심해서 다루기)

| 파일 | 내가 할 수 있는 것 | 할 수 없는 것 |
|---|---|---|
| `src/routes/index.js` | 내 라우트 **한 줄 추가** | 다른 줄 수정, 순서 정리, 포맷 변경 |
| `tests/helpers.js` | 읽기, 사용하기 | 수정 (필요한 도우미는 **내 테스트 파일 안**에 만듭니다) |
| `src/utils/errors.js`, `codes.js` | 읽기, 사용하기 | 수정 (새 코드는 리더에게 요청) |
| `src/models/`, `migrations/` | 읽기 | 수정 (컬럼이 필요하면 요청) |
| `package.json`, `package-lock.json` | 읽기 | 수정 (패키지는 사전 상의) |
| `.env.example`, `src/config/env.js` | 읽기 | 수정 (새 환경변수는 PR 에 적고 확인) |

> **`package-lock.json` 이 바뀌어 있으면 되돌리세요.** `npm install` 을 다시 실행하다가 바뀌는 경우가 있습니다. (`git restore package-lock.json`)

### 4-2-1. 원단 조회를 맡았다면 (파일 이름 주의)
`fabrics.*` 파일(`fabrics.routes.js`, `fabrics.service.js`, `fabrics.dao.js`, `fabrics.schema.js`)은 리더가 원단 등록·수정·삭제에 쓰고 있어서 **고치지 않습니다.** 원단 조회(10·11·14번)는 `fabricsRead.routes.js`, `fabricsRead.service.js`, `fabricsRead.dao.js`, `fabricsRead.schema.js`, `fabricsRead.controller.js`, `tests/fabrics-read.test.js` 처럼 **새 파일**로 만드세요. `routes/index.js` 에는 한 줄만 추가합니다.

### 4-3. 테스트에서 겹치지 않기
- 테스트 파일은 **기능별로 내 파일**을 씁니다. (`tests/patterns.test.js`, `tests/favorites.test.js`, `tests/inquiries.test.js`) 같은 파일을 둘이 고치지 않습니다.
- 테스트는 시작 때 DB 를 비웁니다(`resetDb`). 테스트 파일들은 **하나씩 순서대로** 실행되도록 설정되어 있으니 내 테스트에서 다른 테스트 데이터가 남아 있다고 가정하지 마세요. 테스트에 필요한 데이터는 **테스트 안에서 직접 만듭니다.**
- 테스트 DB 는 이름이 `_test` 로 끝나는 DB 입니다. 개발 DB 의 내 데이터는 테스트가 지우지 않습니다.

### 4-4. DB(테이블)가 바뀌는 경우
- 리더가 공지하면: `git pull origin main` → `npm run migrate` → `npm run migrate:test`
- **내가 DB 를 바꾸고 싶으면** 리더에게 요청합니다. "어떤 테이블에 어떤 컬럼이 왜 필요한지"를 적어 주세요.
- DB 를 직접 만지는 도구(DBeaver 등)로 테이블을 고치지 마세요. 내 DB 만 달라져서 나중에 원인을 찾기 어렵습니다.

## 5. 하루 작업 루틴 (예시)

```
[시작]
1. git switch main && git pull origin main
2. (migrations 에 새 파일이 있다면) npm run migrate && npm run migrate:test
3. git switch feature/내브랜치   (없으면 git switch -c feature/내브랜치)
4. git merge main

[작업]
5. 명세서 번호 하나 → AI 에게 프롬프트(3-2) → 결과 확인(3-4)
6. 작게 커밋:  git add src tests  →  git commit -m "feat(patterns): 도안 목록 조회 API"

## 6. 막혔을 때

| 상황 | 먼저 할 일 | 그래도 안 되면 |
|---|---|---|
| 서버나 테스트가 안 켜짐 | `README.md` 의 "문제가 생기면" 표 | 오류 전체를 리더에게 전달 |
| 테스트가 실패함 | 오류 메시지의 **첫 줄**부터 읽기. AI 에게 4번 프롬프트 사용 | 리더에게 전달 |
| 명세서가 애매함 | 명세서의 "처리 규칙"과 "오류 코드"를 다시 읽기 | **추측하지 말고** 리더에게 질문 |
| 명세서와 다르게 해야 할 것 같음 | 코드를 바꾸지 않기 | 리더에게 이유를 설명 |
| git 충돌이 남 | `CONTRIBUTING.md` 의 "충돌이 났을 때" | 풀지 말고 `git merge --abort` 후 리더에게 문의 |
| 실수로 다른 파일을 고침 | `git restore 파일경로` 로 되돌리기 | 리더에게 문의 |
| 무엇을 해야 할지 모르겠음 | `docs/담당표.md` 의 내 순서 확인 | 리더에게 문의 |

**질문할 때는 이 3가지를 적어 주세요:** ① 무엇을 하려고 했는지 ② 무슨 일이 일어났는지(오류 전체) ③ 이미 시도한 것

- [ ] `npm run lint`, `npm test` 가 통과한다
